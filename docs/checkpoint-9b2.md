Each exposed maxBufferSize **2,147,483,648 bytes** and maxStorageBufferBindingSize **2,147,483,644 bytes**. These are per-buffer limits, not free VRAM or aggregate memory budgets. WebGPU does not provide a general GPU enumeration/free-VRAM API.

The existing AI Lab reports a separate default adapter. Installed Transformers.js `src/backends/onnx.js` already sets ONNX `webgpu.powerPreference = 'high-performance'`; installed ONNX `lib/wasm/wasm-core-impl.ts` passes that hint into requestAdapter. Thus adding the hint alone would not resolve this machine's selection. Chrome's [Windows-specific WebGPU documentation](https://developer.chrome.com/docs/web-platform/webgpu/troubleshooting-tips) describes selection of the same GPU used for other Chrome workloads and the ineffectiveness of the powerPreference hint on Windows. That behavior matches today's probe. It supports a browser/process GPU-selection explanation rather than a missing NVIDIA installation. The exact Windows/OEM policy responsible has not been isolated.

**NVIDIA hardware is detected and healthy in Windows, but NVIDIA WebGPU selection is not demonstrated in the tested browser configuration.** AMD is the only adapter returned. The previous 9B.1 AMD label was a preflight probe, not a captured ONNX GPUDevice; retrospectively proving the exact inference device is impossible from that label alone. Today's matching requests make AMD likely for an equivalent configuration. NVIDIA driver/kernel execution and relative generation speed remain unmeasured. Chrome graphics `supportsDx12`/DirectML fields are not a conclusive WebGPU compatibility test.

### Safe manual Windows selection

1. Save work and note the current preference. Open **Settings → System → Display → Graphics**. Add the actual browser executable as a desktop app if absent. Tested Chrome path: `C:\Program Files\Google\Chrome\Application\chrome.exe`. For Edge, use its installed msedge.exe path shown by `edge://version`; an embedded browser may use a different host executable.
2. Choose that app's **Options/Graphics preference → High performance**, verify it names **NVIDIA GeForce RTX 3050**, then Save. Labels vary across Windows builds. These steps follow [Microsoft's per-app GPU instructions](https://support.microsoft.com/en-au/windows/hardware/display-graphics/optimizations-for-windowed-games-in-windows-11). No settings were changed by this audit.
3. Fully exit and restart the chosen browser, including background processes through its normal controls. Check graphics acceleration in `chrome://settings/system` or Edge's System settings and inspect `chrome://gpu`/`edge://gpu` for hardware-accelerated WebGPU and driver problems. Keep existing safety/blocklist protections; experimental flags are not required by this plan.
4. Rerun the **model-free** adapter probe in that exact executable/profile. The standalone Chrome command is `node scripts/ai-9b2-research.cjs --gpu`; it overwrites only the diagnostic JSON. Verify a NVIDIA adapter and shader-f16, and record its limits. If it still returns AMD, stop; retain Qwen and investigate browser/OEM policy manually. Restore the original Windows preference to undo the change.

Switching adapters is not a measured performance improvement. Rebenchmark on the same selected adapter before attributing latency changes to a model.

## Memory safety assessment

All numbers below are **planning estimates**, not measured peaks or crash-proof ceilings. Quantization reduces many matrix weights, not all embeddings, activations or KV tensors. Browser caches occupy disk separately; downloading a 1.2 GB file can temporarily create several host-memory copies. AMD shared GPU memory competes with system RAM; 16 GB RAM and 4 GB dedicated VRAM must not be added into one interchangeable pool.

Batch 1, no beam search, no persistent chat history, one active request, at most one serialized retry. Sequence cap **1,096 tokens** includes the full 1,024-token input budget and 72 output tokens. Retry must also fit that input cap and release the previous generation's KV cache.

KV storage = `2 × layers × KV heads × head dimension × sequence tokens × bytes per element`. Qwen3: 28/8/128; Qwen2.5: 28/2/128; SmolLM: 24/32/64. q4f16 does not imply 4-bit KV. Qwen3/SmolLM configs declare float16 for q4f16; Qwen2.5 omits that declaration, so budget float32 conservatively until graph metadata proves otherwise. Old and new cache tensors can overlap briefly; budget two copies.

| Candidate | Weights proxy | One KV at 1,096 (fp16 / fp32) | Estimated total GPU footprint including browser reserve | Estimated additional host RAM | Decision |
|---|---:|---:|---:|---:|---|
| Qwen3-1.7B q4f16 | 1.328 GiB | 119.88 / 239.75 MiB | **2.3–4.1 GiB** with fp16 cache; worse if float32 | 3.5–6 GiB | **Reject for this 4 GB trial:** upper planning estimate exceeds physical VRAM |
| Qwen2.5-1.5B q4f16 | 1.138 GiB | 29.97 / 59.94 MiB | **2.0–3.5 GiB**, budgeting float32 cache | **3–5.5 GiB** | Conditional feasibility only; current adapter/RAM gates fail |
| SmolLM2-1.7B q4f16 | 1.033 GiB | 205.50 / 411.00 MiB | **2.1–3.6 GiB** with fp16 cache | 3–5.5 GiB | Marginal alternate; larger KV and less headroom, not selected; reject if float32 cache or preflight headroom cannot be established |

GPU calculation uses roughly one weight payload for resident packed weights, **0.25–1.0 additional payload** for upload/temporary/retained allocations, **two KV copies**, **0.35–0.75 GiB** for runtime activations/logits/scratch and **0.20–0.35 GiB** for browser/graphics overhead. This intentionally conservative overlap is not a proven allocation trace. Host planning allows up to roughly **three weight copies + 1.5 GiB** for parser/WASM/tokenizer/browser/staging, rounded upward. Additional copies, graph transformations or driver allocations can exceed these envelopes; stop on pressure, never escalate to a larger load to diagnose a crash.

At 1,024 input tokens, a full Qwen logits output alone can be about **297 MiB fp16 or 594 MiB fp32** before selection of the final token, explaining the runtime reserve. Attention scratch and intermediates also matter. Estimated fp16 embedding tensors are approximately 593.5 MiB Qwen3, 445.1 MiB Qwen2.5 and 192 MiB SmolLM; all fit today's AMD ~2 GiB single-binding limit, but **actual largest tensor and NVIDIA limits are unverified**. Whole ONNX file size is not a single GPUBuffer size. ONNX requests adapter-supported limits when creating its device; a manually created device using the default 128 MiB binding limit could still fail.

Do not test advertised maximum context: cache and especially prefill tensors grow sharply. Qwen2.5 float32 KV alone at 32,768 tokens is approximately 1.75 GiB, before cache overlap and other allocations. Context extension/YARN, batches, beams, simultaneous models and full-context prompts are excluded.

**Preflight gates:** NVIDIA selected in the actual inference worker; shader-f16; adequate recorded per-buffer limits; **at least 3.8 GiB free dedicated VRAM and 7.5 GiB available system RAM** before candidate load; at least 4 GB free profile/cache disk space. The upper 3.5 GiB GPU plan plus 0.3 GiB headroom sets the VRAM gate. The 5.5 GiB host plan plus 2 GiB reserve sets the RAM gate. Use a short, controlled context; if graph metadata changes the estimate, re-evaluate before generation. Current NVIDIA free memory is approximately 3.72 GiB and RAM 5.72 GiB, and Chrome selects AMD: **do not load now**. If these gates cannot be met after closing discretionary workloads, reject the test on this machine rather than rely on shared-memory spill or swap. These gates reduce risk; they do not establish a measured peak.
